## Сахар arity-перегрузок для extractors

Сегодня (см.
[handlers-response.md](handlers-response.ru.md#типизированное-извлечение-fromrequest))
использование типизированного extractor'а означает ручной вызов
`T.from_request(req)` внутри обычного `Handler`:

```nova
r.get("/users/{id}", fn(req ServerRequest) -> ServerResponse {
    match PathParam[UserId].from_request(req) {
        Ok(p)  => /* ... */
        Err(e) => e.into_response()
    }
})!!
```

Дизайн предполагает, что `Router.@get`/`@post`/`@put`/`@delete`/`@patch`
получат 0–4-extractor'ные перегрузки, чтобы обработчик мог принимать
extractors как голые параметры функции (та же форма, что у Axum'а):

```nova
// PLANNED — not implemented, do not copy this into real code yet.
export fn Router mut @get[T1 FromRequest, R IntoResponse](path str, h fn(T1) -> R) -> Result[Router, HttpError]
```

**Почему это ещё не реализовано**: даже минимально возможная версия этого
сахара — одна новая bound-generic перегрузка на `Router.@get`, вообще без
единого call site — уже ломает кодоген на существующих, не связанных,
не-generic call site'ах `@get(path, Handler)`, которые уже есть в
собственном тестовом наборе этого пакета (несовпадение checker'а/кодогена
на arity-перегрузках, отслеживается выше по потоку, в компиляторе Nova —
не то, что можно обойти локально в этом пакете). Низкоуровневая форма
`Router.@get(path, Handler)` + ручная композиция per-extractor,
показанная по всему набору доков — единственный путь регистрации *под
этими самыми именами методов*, пока этот пробел компилятора не закроется.

**Что уже есть под другим именем**: `Router.@post_typed_h[T FromRequest +
Reflect](path, h fn(T) -> ServerResponse)` — голый обработчик плюс один
type-параметр, тот же эргономичный пункт назначения, что и сахар выше,
зарегистрированный под именем, не коллидирующим с набором перегрузок
`@post` (обходит ровно тот пробел кодогена, что описан в этом разделе). См.
[extractors.md](extractors.ru.md#bare-sugar-регистрация-_typed_h) за полным
описанием — это более узкое, отдельно-именованное семейство (один метод,
только `POST`, один бандл-type-параметр), не 0–4-extractor'ная
одноимённая перегрузка, набросанная выше.

## Переименование `Path[T]`

`PathParam[T]` ([handlers-response.md](handlers-response.ru.md#типизированное-извлечение-fromrequest))
— временное имя. Каноническое имя дизайна — `Path[T]` (паритет с Axum) —
переименовано в `PathParam[T]` только потому, что `Path` сейчас коллидирует
с `std.fs.Path` в некоторых компил-юнитах (дефект кросс-модульного
тайпчека по одинаковому имени, отслеживается выше по потоку). Как только
это закроется, `PathParam[T]` станет `Path[T]`, а `PathParam[T]`
исчезнет — переименование, не новый тип, поведение не меняется.

## Генерация OpenAPI

**Реализовано** (план 222.8 Ф.1–Ф.3) — этот раздел раньше говорил «не
реализовано»; это было устаревшей информацией. `Reflect`/`TypeShape` из
`std.reflect` описывают структурную форму типа,
[`TypedRoute`/`*_typed`/`*_typed_h`](extractors.ru.md#typed-маршруты-typedroute--_typed)
записывают её на каждый route, `Router.introspect()` её сообщает, а
`openapi_json`/`openapi_handler` из [`src/openapi.nv`](../src/openapi.nv)
рендерят документ OpenAPI 3.0 JSON прямо из этих шэйпов — без
промежуточного типа схемы, без макро-эквивалента
`#[derive(OpenApi)]`. Полное описание:
[extractors.md#связь-с-openapi](extractors.ru.md#связь-с-openapi); разобранный
пример: route `/openapi.json` в [`examples/03-json-api`](../examples/03-json-api)
+ его закоммиченный [`openapi.golden.json`](../examples/03-json-api/openapi.golden.json).
Отдельной страницы `openapi.md` (полная форма схемы parameters/requestBody/
responses, правила hoisting'а `components/schemas`) пока нет — сегодня
подробный референс — собственные doc-comment'ы эмиттера в
`src/openapi.nv`.

## Фаза B: нарезка модулей

Корень `src/` пакета сейчас держит большую часть фреймворка как co-equal
«root peer»-файлы (`server.nv`, `response.nv`, `extract.nv`, `middleware.nv`,
`auth.nv`, `multipart.nv`, `background.nv`, `ws_upgrade.nv`, …), все в
`module polaris` — следствие того, что извлечение из `nova-http` приземлилось
одной волной, а не постоянная форма. Следующий проход ожидаемо нарежет их
на собственные суб-модули (по образцу уже существующего разделения
`polaris.ws`/`polaris.net`/`polaris.static`/`polaris.middleware.*`) —
реорганизация, не изменение API; этот набор доков соответственно перенесёт
собственные ссылки на файлы-исходники, когда это случится.

## Валидация запросов

Отдельного слоя валидации сверх того, что уже отклоняет десериализация
`serde` (неверный тип, отсутствующее обязательное поле), пока нет.
Декларативные ограничения в стиле FastAPI (мин/макс длина, числовые
диапазоны, regex, межполевые проверки) не реализованы. Пока это не
появилось — валидируйте вручную в начале обработчика (или внутри
вспомогательной функции, возвращающей `Result` — см.
[errors.md](errors.ru.md#-эргономика-через-бланкет-result)) и возвращайте
типизированную `HttpError` при отказе.

## Сессии: обобщённое хранилище

[`auth.md`](auth.ru.md#сессии) документирует сегодняшний **скелет**
сессий: одна конкретная реализация `MemorySessionStore` за протоколом
`SessionStore`. Обобщённый `session[S SessionStore](store S, ...)` —
чтобы сам `session` не зашивал in-memory реализацию — естественное
продолжение, отложенное до подтверждения безопасности захвата
generic-значения замыканием через границу M:N-фибра для этой формы.

## Graceful shutdown для фоновых задач

[`serving.md`](serving.ru.md#фоновые-задачи) документирует
`BackgroundTasks.@drain()` таким, какой он есть сегодня: вызывается
синхронно драйвером соединения после успешной записи, **без** привязки к
жизненному циклу сервера — потому что в этом пакете пока нет
общего-для-accept-loop graceful-shutdown с дедлайн-дрейном. Рассматриваются
два варианта на выбор, когда он появится: обернуть `@drain()` в
`supervised(deadline:)` на уровне run-loop'а (просто, но молча теряет
задачи, не успевшие стартовать к дедлайну), либо process-wide счётчик
in-flight-задач, который shutdown ждёт с тем же дедлайном (симметрично
собственному lifespan-shutdown FastAPI/Starlette, не теряет уже начатую
работу). Ни один не реализован.
